# Projects Tab — Design

## Problem

As the user pushes into harder grades (V4, V5+), full sends become rare and most sessions produce only "attempts" with no completions. The current Log page treats every climb as binary attempt-or-send, which makes hard-grade sessions look like a wall of orange and obscures the incremental progress that *is* happening — figuring out moves, linking sections, getting closer each time.

We need a way to capture per-route progress on multi-session projects: what the route looks like, which moves you can do, what beta you've worked out, and how many attempts have gone in.

## Solution

A new **Projects** tab. Each project is a photo of a real wall with tappable markers placed on individual holds, where each marker is a "move" with a state (todo / working / done), vocabulary tags, and free-text notes. Logging an attempt against a project bumps a counter; the Log page stays untouched for warmups and flash-grade climbs.

Progress on hard projects becomes visible in two ways: marker states fill in over weeks, and per-project attempt counts accumulate even when the route isn't sent.

## Data model

### New tables

```ts
projects: defineTable({
  userId: v.string(),
  name: v.string(),                    // user-supplied
  grade: v.string(),                   // "V5"
  holdType: v.string(),                // "crimp" | "jug" | "sloper"
  photoStorageId: v.id("_storage"),    // Convex file storage
  status: v.union(
    v.literal("active"),
    v.literal("sent"),
  ),
  createdAt: v.number(),
  sentAt: v.optional(v.number()),      // set when status flips to "sent"
})
  .index("by_user_status", ["userId", "status"])
  .index("by_user", ["userId"]),

projectMoves: defineTable({
  projectId: v.id("projects"),
  userId: v.string(),                  // denormalized for query authorization
  order: v.number(),                   // 1, 2, 3... tap order; gaps allowed
  x: v.number(),                       // 0..1, fraction of photo width
  y: v.number(),                       // 0..1, fraction of photo height
  state: v.union(
    v.literal("todo"),
    v.literal("working"),
    v.literal("done"),
  ),
  vocabTags: v.array(v.string()),      // VocabId[]
  notes: v.string(),                   // free text, default ""
})
  .index("by_project", ["projectId"]),
```

**Why fractional x/y:** photos render at different sizes across viewports. Storing positions as `0..1` of photo dimensions keeps markers locked to the right hold regardless of screen size or orientation.

**Why a separate `projectMoves` table** (vs. embedding moves as an array on `projects`): Convex documents have a 1MB limit and any update rewrites the whole document. With a separate table, toggling one move's state is a small targeted write rather than rewriting the entire project including the photo metadata and every other move's state.

### Modified table

```ts
climbs: defineTable({
  // ...all existing fields unchanged
  projectId: v.optional(v.id("projects")),  // NEW, nullable
})
```

Existing rows have `undefined` projectId — backward-compatible. Quick log on the Log page produces rows with no `projectId` (current behavior); project-page "+attempt" produces rows with `projectId` set.

### Card contents

- Photo thumbnail (~64px square)
- Project name
- Grade chip + hold type icon (matching log page conventions)
- **Move-state dots**: N filled circles, color = state (gray/blue/green)
- Footer: "X attempts · Y session days" — rolled up from `climbs` joined on `projectId`

### Subtabs

- **Active** — `status === "active"`, sorted by most-recently-attempted descending
- **Sent** — `status === "sent"`, sorted by `sentAt` descending. Same card layout; dots all green.

URL state: subtab driven by `?status=sent` search param on `/projects`, not a separate route.

### Empty states

- No active projects → "No projects yet. Tap + to start one." centered, muted
- No sent projects → "Send your first project and it'll show up here." muted

### "+" FAB

Bottom-right floating action button → navigates to `/projects/new`.

### Performance

Computing attempt rollups requires joining `climbs` to projects. To avoid N+1, expose a single Convex query `projects.listWithRollups` that returns projects already zipped with `{ attempts, sessionDays }`. Implementation can scan climbs by `userId` once and group by `projectId` in memory; for current data volumes this is well within Convex's per-query budget.

### Header

- Back chevron → `/projects`
- Project name
- Overflow menu `[⋯]`: Rename, Delete project
- Subline: grade + hold type icon + progress dots (matches list card)

### Canvas gestures

- **Tap empty area** → drop next-numbered marker at that fractional coord; starts in `todo`
- **Tap a marker** → open move detail bottom sheet
- **Long-press a marker (200ms)** → drag to reposition; release on lift; clamp to `0..1` bounds
- **Pinch / double-tap** → zoom photo (markers scale with it; positions remain fractional of original photo)

The 200ms hold threshold distinguishes drag from tap, preventing accidental marker drops during pan or pinch.

### Marker rendering

- Each marker is a numbered circle, color-coded by state:
  - `todo` — gray fill, dark border
  - `working` — blue fill, dashed border
  - `done` — green fill, solid border
- Markers positioned via `style={{ left: \`${x*100}%\`, top: \`${y*100}%\` }}` on an absolute-positioned overlay element

### Hint text

"Tap a hold to add a move" appears below canvas when project has zero markers; fades out after the first marker is added.

### Footer

- Inline summary: "N / total done · X attempts" — `total` is the count of `projectMoves`, `done` is moves with `state === "done"`, `attempts` is `climbs` rows where `projectId` matches
- "+ attempt today" button — writes a `climbs` row with `projectId`, current `grade`, `holdType`, `completed: false`, `climbedAt: now`. Does not change any move state

### Auto-send on all done

When the last `todo`/`working` move flips to `done`:

1. `projects.status` flips to `"sent"`, `sentAt = Date.now()`
2. Toast appears: *"Project sent! Moved to Sent."* with an "Undo" action visible for 5 seconds
3. Tapping Undo reverts the status flip and the most recent move state change

Conversely: if a move on a `"sent"` project is reverted to `working` or `todo` (or a new move is added), `projects.status` flips back to `"active"` automatically. `sentAt` is cleared.

### Edge cases

- Adding a move to a "sent" project → auto-flips back to "active"
- Dragging a marker outside photo bounds → coords clamp to `[0, 1]`
- Deleting a move → remaining moves keep their original `order` numbers (gaps allowed). Renumber-on-delete would be confusing for users who memorized "move 4 is the crux"

### Photo step

- Single tap-to-pick affordance using `<input type="file" accept="image/*" capture="environment">` — on iOS/Android this offers Camera or Library natively
- After pick, the box flips to a thumbnail preview with a "Retake" link
- Resize-and-upload runs immediately on pick — by the time the user finishes naming, upload is usually done
- Small spinner overlay on thumbnail while uploading

### Image resize

Client-side downscale before upload via `<canvas>`:

- Max 1600px on the long edge
- JPEG quality 0.85
- Typical output: 200–400 KB (vs. 4–8 MB original)

Lives in `src/lib/image-resize.ts`.

### Validation

- Name required (non-empty)
- Photo upload must complete before "Create project" enables
- Grade and hold type reuse existing pickers, so they always have a value
- Upload failures show inline error with a "Try again" button

### After create

- `mutation create` returns the new `projectId`
- Redirect to `/projects/$projectId`
- Photo is already there, ready for marker placement

### Photo storage

Convex file storage:

```ts
export const generateUploadUrl = mutation({
  args: {},
  handler: async (ctx) => ctx.storage.generateUploadUrl(),
});

export const create = mutation({
  args: {
    name: v.string(),
    grade: v.string(),
    holdType: v.string(),
    photoStorageId: v.id("_storage"),
  },
  handler: async (ctx, args) => {
    const userId = await requireUser(ctx);
    return await ctx.db.insert("projects", {
      ...args,
      userId,
      status: "active",
      createdAt: Date.now(),
    });
  },
});
```

Reads use `ctx.storage.getUrl(photoStorageId)` to mint short-lived signed URLs on demand. Convex's reactive queries handle URL refresh automatically.

### Privacy

Photos may include other climbers' faces. v1 ships without face-blur or content disclaimer tooling — flagged here as a future consideration, not in scope for first release.

## Testing

The repo does not currently have a test runner configured (verify before implementation). Plan:

1. **Convex function tests** — `projects.create`, `projectMoves.toggleState`, `projects.archive`, and the auto-send-on-all-done invariant. Pure logic, easy to cover if Convex test framework is set up.
2. **Manual UI verification** — gesture interactions on a real phone (tap vs long-press, drag, marker positioning across orientations, pinch-zoom). Per project conventions, UI changes need device verification before claiming done.

If no testing infrastructure exists today, recommend manual verification for v1 and adding test infrastructure as a separate spec rather than bundling it.
